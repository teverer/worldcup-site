## 六、文档写作约定（给人和 AI）

文档只写「意图、边界、验收」，不写会把后续实现钉死的细节。

- **可以精确**：数据事实、统计口径、命名、颜色 / 字体令牌、验收阈值、安全 / 版权边界。
- **不要写**：像素值、列数、具体 class / 选择器、某一版的布局处方、动画时长。
- **具体做法**写进带日期的「实现记录」，并标「可替换」；不与规格混写。
- **负面规则写意图**：例如写「不要满屏白卡」，而不是「不要卡片」；不要把某一期的绝对禁令写成永久规则。
- **一个事实只在一处维护**；其他文档链接，不复制。过期决策保留原文并标「已推翻 + 原因」。
- **判断**：这句话如果明天数据 / 宽度 / 内容变了，会不会变成错的？会 → 写意图 + 验收；不会 → 可以写事实。
- **单一规格源**：设计规格以 `设计改造-00-总纲.md` 为准；感觉与工作流看 `设计改造-01`；项目上下文只记背景，不记当前规格。

## 推荐阅读顺序

1. **项目说明** —— 先把项目在自己电脑上跑起来
2. **编码规范 + Git 规则 + 界面设计规范** —— 写代码前
3. **需求 + 设计 + 数据来源** —— 查功能、字段、统计口径
4. **项目上下文** —— 接手排错或需要了解"为什么这样做"时
5. **设计改造总纲 + 感觉与工作流** —— 改 UI 前
